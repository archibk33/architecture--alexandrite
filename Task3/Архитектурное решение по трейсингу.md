# Архитектурное решение по трейсингу

Проведен анализ текущей архитектуры и рассмотрены варианты по использованию трейсинга 

## Анализ системы и проблемных мест

### Критические точки отказа для заказов

**1. Internet Shop → Shop API → Shop DB**
- Пользователь создаёт заказ, загружает 3D файл
- *Что может сломаться:* таймауты при загрузке больших файлов, ошибки валидации, проблемы с записью в БД

**2. Shop API → 3D files storage (S3)**
- Сохранение 3D модели в хранилище
- *Что может сломаться:* S3 недоступен, файл повреждён, нет места в storage

**3. Shop API → RabbitMQ → MES API**
- Отправка заказа на расчёт стоимости
- *Что может сломаться:* RabbitMQ недоступен, сообщение потеряно, MES API не отвечает

**4. MES API → 3D files storage → расчёт стоимости**
- MES читает файл и считает стоимость 
- *Что может сломаться:* файл не найден, алгоритм расчёта висит, нехватка ресурсов

**5. MES API → RabbitMQ → CRM API**
- Результат расчёта отправляется в CRM
- *Что может сломаться:* сообщение потеряно, CRM API недоступен

**6. CRM → подтверждение → RabbitMQ → MES API**
- Продавец подтверждает заказ
- *Что может сломаться:* продавец не видит заказ, сообщение не дошло до MES

**7. MES → операторы → обновления статусов**
- Операторы берут заказ в работу
- *Что может сломаться:* операторы не видят заказ, статусы не обновляются

### Дополнительные проблемные места

**API users (B2B клиенты)**
- Они напрямую обращаются к MES API
- Ещё сложнее отследить их заказы
- Нет единого correlation ID между системами

**Асинхронные процессы**
- Расчёт стоимости может занимать до 30 минут
- Нет способа понять, на каком этапе расчёт сейчас

## Данные для трейсинга

Вот что нам нужно собирать, чтобы восстановить полную картину

### Базовые данные трейсинга
- **Correlation ID** - уникальный идентификатор заказа через все системы
- **Timestamp** - точное время каждого события
- **Service name** - какой сервис обрабатывает запрос
- **Operation name** - что именно делает сервис
- **User ID** - кто инициировал операцию
- **Session ID** - сессия пользователя (для B2C)

### Бизнес-данные заказа
- **Order ID** - идентификатор заказа в каждой системе
- **Order status** - текущий статус заказа
- **File path** - путь к 3D-файлу в S3
- **File size** - размер 3D-модели
- **Customer type** - B2C или B2B клиент
- **Calculation complexity** - сложность расчёта (простая/средняя/сложная)

### Технические данные
- **HTTP method** и **endpoint** - куда и как пришёл запрос
- **Response code** - успешно или с ошибкой
- **Response time** - сколько времени заняла операция
- **Queue name** - в какую очередь RabbitMQ отправлено
- **Message ID** - идентификатор сообщения в очереди
- **Error details** - подробности ошибки если что то пошло не так

### Контекстные данные
- **IP address** - откуда пришёл запрос
- **User agent** - что за браузер/приложение
- **Operator ID** - какой оператор взял заказ в работу
- **Seller ID** - какой продавец подтвердил заказ

## Мотивация

### Почему нам критически нужен трейсинг

Сейчас при обращении клиента с жалобой «мой заказ пропал» процесс поиска превращается в трудоёмкое и хаотичное расследование.
Проверка начинается с базы данных Shop DB, где заказ присутствует. Затем анализируется система MES, где заказ отсутствует. После этого приходится изучать очереди RabbitMQ, при этом зачастую нет возможности достоверно установить, какие сообщения проходили, например, вчера.

В результате поиск одного заказа занимает часы, сопровождается значительными трудозатратами и отсутствием прозрачности, а клиент всё это время ожидает решения.


**Что даст нам трейсинг:**

1. **Видимость пути заказа** - увидим весь путь от создания до завершения
2. **Быстрая диагностика** - найдём проблему за минуты, а не часы
3. **Проактивное решение проблем** - увидим, где заказы застревают чаще всего
4. **Доказательства для клиентов** - сможем точно сказать, что и когда произошло

### Влияние на технические метрики

**1. Mean Time To Resolution (MTTR)**
- *Текущее состояние:* 4, 8 часов на поиск проблемы
- *С трейсингом:* 15, 30 минут
- *Улучшение:* в 10, 15 раз

**2. First Call Resolution Rate**
- *Текущее состояние:* 30% (часто нужны дополнительные расследования)
- *С трейсингом:* 80% (сразу видим что произошло)
- *Улучшение:* в 2.5 раза

**3. System Observability Score**
- *Текущее состояние:* 20% (почти слепые)
- *С трейсингом:* 85% (видим весь путь заказа)
- *Улучшение:* в 4 раза

### Влияние на бизнес-метрики

**1. Customer Satisfaction Score (CSAT)**
- *Текущее состояние:* жалобы на потерянные заказы
- *С трейсингом:* быстрое решение проблем, прозрачность
- *Ожидаемое улучшение:* +25% CSAT

**2. Order Loss Rate**
- *Текущее состояние:* ~5% заказов теряются или зависают
- *С трейсингом:* проактивное выявление проблем
- *Ожидаемое улучшение:* снижение до 1%

**3. Support Team Productivity**
- *Текущее состояние:* много времени на поиск проблем
- *С трейсингом:* больше времени на решение реальных проблем клиентов
- *Ожидаемое улучшение:* +40% производительности

**4. Revenue Protection**
- *Текущее состояние:* теряем B2B контракты из-за проблем с API
- *С трейсингом:* быстрое решение проблем партнёров
- *Ожидаемый эффект:* сохранение 2-3 крупных контрактов в год

## Предлагаемое решение

### Выбор технологии

Я изучил разные варианты и думаю, что нам подойдёт **Jaeger**.

- **Open source** - не привязываемся к проприетарным решениям
- **Совместимость с OpenTracing** - стандартный API
- **Хорошая интеграция** с Spring Boot (у нас Java) и .NET (у нас C# в MES)
- **Elasticsearch storage** - можем использовать как часть ELK стека
- **Grafana integration** - объединим с мониторингом

### Архитектура трейсинга

**Jaeger Agent** на каждом сервере приложений
- Собирает spans от приложений
- Буферизует и отправляет в Collector

**Jaeger Collector** 
- Принимает данные от агентов
- Валидирует и сохраняет в Elasticsearch

**Jaeger Query Service**
- API для поиска трейсов
- Web UI для визуализации

**Elasticsearch** 
- Хранилище трейсов
- Индексирование для быстрого поиска

### Инструментация приложений

**Shop API (Spring Boot)**
```java
// Автоматическое создание spans для HTTP запросов
@RestController
public class OrderController {
    @Autowired
    private Tracer tracer;
    
    @PostMapping("/orders")
    public ResponseEntity<Order> createOrder(@RequestBody Order order) {
        Span span = tracer.nextSpan().name("create-order").start();
        try (Tracer.SpanInScope ws = tracer.withSpanInScope(span)) {
            span.tag("order.id", order.getId());
            span.tag("customer.type", "B2C");
            // логика создания заказа
            return ResponseEntity.ok(order);
        } finally {
            span.end();
        }
    }
}
```

## Компромиссы

### Когда трейсинг не поможет

Могу предположить, что есть ситуации где трейсинг бесполезен или слишком дорог

**1. Проприетарные системы**
У нас есть купленная MES система. Если вендор не предоставит API для трейсинга, мы можем отслеживать только "вход" и "выход" из системы, но не внутренние процессы.

**2. Legacy код без изменений**
Некоторые части системы могут быть настолько старыми, что добавление трейсинга потребует больших переделок. Возможно, проще сначала отрефакторить.

**3. Высоконагруженные операции**
Трейсинг каждого запроса добавляет overhead. Для очень частых операций (например, health checks) может потребоваться sampling.

**4. Чувствительные данные**
Некоторые данные нельзя логировать в трейсах (персональные данные, пароли). Нужна тщательная настройка того, что записывать.

**5. Сетевые проблемы**
Если проблема в сетевой инфраструктуре (роутеры, файрволы), трейсинг приложений не поможет. Нужен отдельный network monitoring.

### Ограничения реализации

**Производительность**
- Трейсинг добавляет 1, 5% overhead к response time
- Требует дополнительную память для буферизации spans
- Elasticsearch нужен для хранения (дополнительные ресурсы)

**Сложность**
- Нужно обучить команду работе с Jaeger UI
- Требуется дисциплина в инструментации кода
- Может усложнить отладку если неправильно настроено

**Стоимость**
- Дополнительная инфраструктура (Jaeger + Elasticsearch)
- Время разработчиков на инструментацию
- Ongoing поддержка и настройка

### Что делать с ограничениями

**Поэтапное внедрение**
- Начнём с критического пути заказа
- Постепенно добавим остальные компоненты
- Сначала manual instrumentation, потом automatic

**Sampling strategy**  
- 100% трейсинг для ошибок
- 10% sampling для успешных операций в production
- 100% в dev/staging окружениях

**Retention policy**
- Детальные трейсы храним 7 дней
- Агрегированные данные - 90 дней
- Критические события - 1 год

## Аспекты безопасности

### Защита данных трейсинга

**Аутентификация и авторизация**
- Jaeger UI доступен только авторизованным пользователям
- Интеграция с корпоративным Active Directory
- Разные уровни доступа:
  - **Support team** - полный доступ к трейсам
  - **Developers** - доступ к техническим данным
  - **Management** - только агрегированная статистика

**Шифрование**
- HTTPS для всех соединений с Jaeger UI
- TLS для связи между Jaeger компонентами
- Шифрование данных в Elasticsearch at rest

**Фильтрация чувствительных данных**
- Автоматическое удаление PII (персональных данных)
- Маскирование номеров карт, паролей
- Хеширование customer ID в трейсах

**Audit logging**
- Логирование всех обращений к Jaeger UI
- Отслеживание кто и какие трейсы просматривал
- Интеграция с SIEM системой

**Сетевая безопасность**
- Jaeger компоненты в приватной сети
- Firewall rules только для необходимых портов
- VPN доступ для внешних подрядчиков

### Внешний доступ

Пока не планируем давать доступ к трейсингу внешним пользователям (клиентам, партнёрам). Это только для внутреннего использования команды.

Если в будущем захотим показывать статус заказа клиентам, сделаем отдельный публичный API на основе данных трейсинга, но без технических подробностей.

### Автоматическое выявление проблем заказов

**1. Зависшие заказы (Stuck Orders)**
```yaml
# Правило алертинга
alert_rule: "stuck_order"
condition: |
  trace.duration > 30min AND 
  trace.status == "incomplete" AND
  no_new_spans_for > 10min
action: |
  - alert: "CRITICAL: Order stuck for 30+ minutes"
  - assign_to: support_team
  - include: order_id, last_service, customer_type
```

**2. Циклические зависимости**
```yaml
alert_rule: "order_loop"
condition: |
  same_service_visited > 3 AND
  trace.duration > expected_duration * 2
action: |
  - alert: "WARNING: Order appears to be in loop"
  - auto_action: kill_problematic_process
```

**3. Высокий error rate по типам заказов**
```yaml  
alert_rule: "order_type_errors"
condition: |
  error_rate_by_customer_type.b2b > 10% OR
  error_rate_by_file_complexity.complex > 20%
action: |
  - alert: "Order processing degradation detected" 
  - escalate_after: 5min
```

**4. Аномальное время расчёта стоимости**
```yaml
alert_rule: "calculation_anomaly"
condition: |
  calculation_time > p99_baseline * 1.5 AND
  file_size < 10MB  # должно быть быстро для маленьких файлов
action: |
  - alert: "MES calculation performance degraded"
  - auto_scale: mes_calculation_workers
```

### Проактивные алерты

**Предсказание проблем на основе трендов:**

**1. Растущая очередь расчётов**
- Анализируем количество заказов в статусе "расчёт стоимости"
- Если рост > 20% за час → алерт "Queue buildup predicted"
- Автоматическое масштабирование MES worker'ов

**2. Деградация производительности**
- Скользящее среднее времени обработки заказов
- Если p95 latency растёт 3 периода подряд → "Performance degradation trend"
- Проверка ресурсов серверов

**3. Сезонные аномалии**
- ML-модель на основе исторических данных трейсинга
- Выявление необычных паттернов заказов
- Раннее предупреждение о возможной перегрузке

### Автоматические действия на основе трейсинга

**1. Auto-healing для зависших заказов**

```python
def auto_heal_stuck_order(trace_data):
    if trace_data.last_service == "mes_api":
        # Рестарт расчёта стоимости
        restart_calculation_job(trace_data.order_id)
        
    elif trace_data.last_service == "rabbitmq":
        # Повторная отправка сообщения
        resend_message(trace_data.correlation_id)
        
    elif trace_data.last_service == "shop_api":
        # Проверка статуса в БД и синхронизация
        sync_order_status(trace_data.order_id)
```

**2. Динамическое масштабирование**
```python
def auto_scale_based_on_traces():
    # Анализ текущих активных трейсов
    active_calculations = count_active_traces("calculate_price")
    queue_depth = get_rabbitmq_queue_depth("price_calculation")
    
    if active_calculations > threshold and queue_depth > 100:
        scale_up_mes_workers(instances=2)
        
    elif active_calculations < threshold * 0.3:
        scale_down_mes_workers(instances=1)
```

**Что требует человеческого вмешательства:**
- Проблемы с данными клиентов
- Изменение бизнес-логики
- Проблемы с внешними API
- Решения о компенсациях клиентам

**Fail-safe механизмы:**
- Все автоматические действия логируются
- Возможность отключить auto-healing для критических операций
- Manual override для операторов
- Rollback автоматических изменений

# Выводы

Внедрение распределённого трейсинга позволит перейти от реактивной модели реагирования на инциденты к проактивному управлению качеством сервисов, предотвращая проблемы до их проявления.
Трассировка заказов должна стать обязательным элементом архитектуры. При корректной реализации она обеспечит полный контроль над движением заказа по всем системам и позволит локализовать сбой за секунды, а не часы.
Несмотря на требуемые затраты на инструментирование кода, настройку инфраструктуры и обучение персонала, эффект в виде сокращения времени диагностики, повышения прозрачности процессов и роста удовлетворённости клиентов многократно превысит вложения.
Рекомендуется начать с внедрения трейсинга на критическом пути обработки B2C-заказов, затем расширить покрытие на B2B-интеграции и остальные бизнес-процессы. Даже частичное покрытие ключевых операций существенно повысит управляемость системы по сравнению с её текущим состоянием.
