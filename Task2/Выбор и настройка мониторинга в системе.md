# Выбор и настройка мониторинга в системе

## Мотивация

### Почему нам срочно нужен мониторинг

На данный момент ситуация с мониотрингом плачевная. Мы узнаём о проблемах от клиентов, а не от системы. 

**Что нам даст мониторинг:**

1. **Перестанем работать вслепую** - будем видеть, что происходит в системе прямо сейчас
2. **Узнаем о проблемах раньше клиентов** - система сама будет сигнализировать о пробюлемах
3. **Сможем планировать ресурсы** - поймём, когда нужно добавлять сервера
4. **Докажем бизнесу эффект от улучшений** - покажет отчеты и цифры


**Бизнес-выгоды:**
- Снижение времени простоя системы (меньше потерянных заказов)
- Улучшение клиентского опыта (проблемы решаются быстрее)
- Экономия на поддержке (не тратим часы на поиск проблем)
- Возможность планировать развитие на основе данных

## Выбор подхода к мониторингу

Я изучил разные подходы и думаю, что нам подойдёт комбинированный вариант, а именно:

### Для приложений: RED метрики

**RED** = Rate (количество запросов), Errors (ошибки), Duration (время отклика)

Это идеально подходит для наших API | Shop API, CRM API, MES API. Просто и понятно:
- Сколько запросов приходит
- Сколько из них с ошибками  
- Как быстро отвечаем

### Для инфраструктуры: USE метрики  

**USE** = Utilization (использование), Saturation (насыщенность), Errors (ошибки)

Для серверов, баз данных, RabbitMQ:
- Насколько загружены ресурсы
- Не перегружены ли они
- Есть ли ошибки на уровне железа

Я думаю, такая комбинация даст нам полную картину происходящего.

## Какие метрики будем отслеживать

Из предложенного списка я выбрал те метрики, которые реально помогут нам понять, что происходит. Объясню каждую:

### Критически важные метрики

**Number of dead-letter-exchange letters in RabbitMQ**
- *Зачем:* Основная проблема: cообщения попадают в dead letter queue, когда что-то идёт не так. 
- *Ярлыки:* queue_name, reason (timeout, reject, max_retries)
- *Алерт:* Больше 5 сообщений за 5 минут (+-)

**Number of message in flight in RabbitMQ**
- *Зачем:* Показывает, сколько сообщений в процессе обработки. Если много, то система не справляется
- *Ярлыки:* queue_name, consumer_tag
- *Алерт:* Больше 100 сообщений в одной очереди (+-)

### Метрики производительности API

**Number of requests (RPS) для всех API**
- *Зачем:* Для понимания нагрузки на каждый сервис, можем планировать масштабирование
- *Ярлыки:* service_name, endpoint, method
- *Пример:* shop_api_orders_post, crm_api_orders_get

**Response time (latency) для всех API**
- *Зачем:* Основная метрика пользовательского опыта. Медленно отвечаем == недовольные клиенты
- *Ярлыки:* service_name, endpoint, percentile 
   (p50 - время, быстрее которого отвечают 50% запросов (средний пользовательский опыт) 
    p95 - быстрее которого отвечают 95% запросов (опыт большинства)
    p99 - почти все запросы )
- *Алерт:* p95 > 2 секунд для критических endpoint'ов

**Number of HTTP 500 и HTTP 200 для всех API**
- *Зачем:* Error rate, ключевая метрика стабильности. Если много кода 500, то со-но проблемы
- *Ярлыки:* service_name, endpoint, status_code
- *Алерт:* Error rate > 5% за 5 минут

### Метрики ресурсов

**CPU % и Memory Utilisation для всех API**
- *Зачем:* Понимаем, не перегружены ли сервера, когда добавлять ресурсы
- *Ярлыки:* service_name, instance_id
- *Алерт:* CPU > 80% или Memory > 85% больше 10 минут

**Memory Utilisation и Number of connections для БД**
- *Зачем :* База данных , узкое место системы, надо следить внимательно
- *Ярлыки:* db_name, instance_role (master/slave)
- *Алерт:* Connections > 80% от максимума

**Size of S3 storage**
- *Зачем:* 3D файлы могут быстро забить хранилище, нужно планировать
- *Ярлыки:* bucket_name, storage_class
- *Алерт:* Рост больше 20% за неделю

### Бизнес-метрики (дополнительно)

Я бы ещё добавил несколько метрик, которых нет в списке, но они важны для бизнеса:

**Orders processing time by status**
- Время между сменами статусов заказа
- Поможет понять, где заказы застревают

**Failed 3D model calculations**  
- Количество неудачных расчётов стоимости
- Ярлыки: error_type, model_complexity

**Operator throughput**
- Сколько заказов обрабатывает каждый оператор
- Поможет оптимизировать нагрузку

## План действий

Вот что я вижу как план реализации мониторинга:

### Этап 1: Базовая инфраструктура (2-3 недели)
1. **Развернуть Prometheus сервер** в облаке на отдельном инстансе
2. **Поставить Grafana** для визуализации метрик  
3. **Настроить AlertManager** для уведомлений в Slack/email/Пачка/Матермост/Макс/Телеграм
4. **Создать базовые dashboards** для каждого сервиса

### Этап 2: Инструментация приложений (3-4 недели)
1. **Добавить Prometheus client libraries** в Shop API, CRM API, MES API
2. **Инструментировать HTTP handler'ы** для сбора RED метрик
3. **Добавить business-метрики** в код приложений
4. **Настроить сбор метрик из RabbitMQ** через специальный плагин

### Этап 3: Инфраструктурные метрики (1-2 недели)  
1. **Установить node_exporter** на все сервера для метрик ОС
2. **Настроить postgres_exporter** для метрик PostgreSQL
3. **Подключить CloudWatch метрики** для S3 и других AWS сервисов

### Этап 4: Алертинг (1 неделя)
1. **Настроить критические алерты** для потери заказов
2. **Добавить алерты на производительность** (latency, error rate)
3. **Создать runbook'и** - что делать когда сработал алерт

### Этап 5: Оптимизация (ongoing)
1. **Настроить retention policy** - сколько хранить метрики
2. **Оптимизировать dashboard'ы** на основе обратной связи
3. **Добавлять новые метрики** по мере необходимости

## Показатели насыщенности (Дополнительное задание)

На мой взгляд, я бы выделил следующие показатели насыщенности.

### CPU насыщенность
- **Пороговое значение:** 80% загрузки CPU больше 10 минут
- **Почему именно этот показатель:** 
  - При 80%+ загрузке система становится нестабильной, response time растёт
  - 10 минут, в целом достаточно времени, чтобы исключить временные пики
  - У нас Java приложения, которые при высокой нагрузке начинают тратить много времени на GC (обратить внимание)
- **Что должно происходить:**
  - Автоматический алерт в Slack/Пачка. Например канал #alerts
  - Запуск дополнительных инстансов через auto-scaling группы
  - Если > 90% больше 5 минут, то экстренный звонок инженеру

### Memory насыщенность  
- **Пороговое значение:** 85% использования памяти больше 5 минут
- **Почему именно этот показатель:**
  - При 85%+ начинается активное использование swap, всё жутко тормозит
  - 5 минут, memory leak может развиваться быстро
  - PostgreSQL особенно чувствителен к нехватке памяти
- **Что должно происходить:**
  - Алерт в Slack/Пачка + email инфраструктурнгой команде   
  - Автоматический restart сервиса если > 95% (emergency mode)
  - Создание дампа памяти для анализа утечек

### Database connections насыщенность
- **Пороговое значение:** 80% от max_connections (у нас max=100, значит > 80)
- **Почему именно этот показатель:**
  - При превышении лимита новые подключения отклоняются с ошибкой
  - Connection pool exhaustion частая причина недоступности сервиса
  - У нас все приложения используют одну БД, connections быстро заканчиваются
- **Что должно происходить:**
  - Немедленный алерт DevOps + DBA
  - Автоматическое увеличение connection pool на стороне приложений
  - Если > 95% временное увеличение max_connections в PostgreSQL

### RabbitMQ queue насыщенность
- **Пороговое значение:** Более 1000 сообщений в одной очереди
- **Почему именно этот показатель:**
  - Значит consumers не справляются с нагрузкой (наша основная проблема)
  - При больших очередях растёт memory usage RabbitMQ
  - 1000 сообщений = примерно 1000 заказов могут зависнуть
- **Что должно происходить:**
  - Критический алерт + звонок инженеру
  - Автоматическое масштабирование consumers (если можно)
  - Активация дополнительных MES операторов

### Disk space насыщенность
- **Пороговое значение:** 80% заполнения диска
- **Почему именно этот показатель:**
  - При 90%+ могут начаться проблемы с записью логов и данных
  - S3 файлы растут быстро (3D модели могут быть большими)
  - PostgreSQL нужно место для temporary tables
- **Что должно происходить:**
  - Алерт с планированием увеличения диска
  - Автоматическое увеличение размера диска в облаке
  - Cleanup старых логов и temporary файлов
  - Если > 95%, то экстренная очистка + алерт

### API Response Time насыщенность  
- **Пороговое значение:** p95 latency > 3 секунды для критических endpoint'ов
- **Почему именно этот показатель:**
  - 3 секунды, психологический порог, когда пользователи начинают нервничать
  - p95 показывает проблемы лучше чем среднее значение
  - Критические endpoint'ы: создание заказа, расчёт стоимости, список заказов MES
- **Что должно происходить:**
  - Алерт команде разработки
  - Автоматическое включение дополнительного кеширования
  - Анализ медленных запросов в БД

### Error Rate насыщенность
- **Пороговое значение:** > 5% HTTP 5xx ошибок за последние 5 минут
- **Почему именно этот показатель:**
  - 5% ошибок == каждый 20-й запрос не работает
  - 5 минут достаточно для исключения случайных всплесков
  - 5xx ошибки == проблемы на нашей стороне (не клиентские ошибки)
- **Что должно происходить:**
  - Критический алерт + немедленное расследование
  - Автоматический rollback последнего деплоя (если был недавно)
  - Включение circuit breakers для защиты downstream сервисов

## Автоматизация реакций на насыщенность

По сути нужны автоматические действия,  то тесть:

### Уровень 1: Preventive (предотвращение)
- Auto scaling при росте нагрузки
- Автоматическая очистка temporary данных
- Preemptive кеширование при росте latency

### Уровень 2: Reactive (реагирование)  
- Алерты в Slack/email/Пачка/Матермост/Макс/Телеграм при превышении порогов
- Автоматические restarts проблемных сервисов
- Увеличение ресурсов в облаке

### Уровень 3: Emergency (экстренное)
- Звонки инженеру при критических проблемах
- Автоматические rollback'и при массовых ошибках
- Включение "режима выживания" (отключение некритических функций)

Мне кажется, такая многоуровневая система поможет нам не доводить до критических ситуаций, а решать проблемы на ранней стадии.
