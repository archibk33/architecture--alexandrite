# Архитектурное решение по кешированию

## Анализ проблем производительности

### Текущие проблемы в системе

**1. Медленная загрузка MES интерфейса**
Операторы жалуются на долгую загрузку первой страницы MES, которая содержит дашборд со списком заказов в работе. Страница показывает заказы по статусам с фильтрацией и пагинацией, но это не решает проблему производительности.

**2. Неэффективные запросы к базе данных**
Каждое обращение к списку заказов требует выполнения сложных SQL запросов с JOIN'ами между таблицами заказов, операторов и статусов. При росте количества заказов производительность только ухудшается.

**3. Отсутствие кеширования повторяющихся данных**
Операторы постоянно обновляют страницу для проверки новых заказов, что приводит к повторным запросам одних и тех же данных к базе данных.

**4. Проблемы со скоростью выполнения заказов**
B2B клиенты недовольны общей скоростью обработки заказов, что частично связано с медленной работой операторов из-за тормозящего интерфейса.

## Мотеивация

### Почему необходимо кеширование

**Основные болевые точки:**
1. **Снижение производительности операторов** - медленный интерфейс напрямую влияет на скорость обработки заказов
2. **Рост нагрузки на базу данных** - каждый запрос к списку заказов создает нагрузку на MES DB
3. **Плохой пользовательский опыт** - операторы тратят время на ожидание загрузки вместо работы с заказами
4. **Потеря конкурентоспособности** - медленная обработка заказов отталкивает B2B клиентов

**Что даст кеширование:**
1. **Ускорение интерфейса операторов** - мгновенная загрузка списков заказов
2. **Снижение нагрузки на БД** - большинство запросов будут обслуживаться из кеша
3. **Улучшение пропускной способности** - операторы смогут обрабатывать больше заказов в единицу времени
4. **Повышение удовлетворенности клиентов** - быстрая обработка заказов улучшит репутацию

### Влияние на технические метрики

**1. Page Load Time**
Текущее состояние: 5, 8 секунд загрузки списка заказов
С кешированием: 0.5, 1 секунда загрузки
Улучшение: в 8, 10 раз

**2. Database Query Load**
Текущее состояние: 100% запросов идут в БД
С кешированием: 20% запросов идут в БД (80% cache hit rate)
Улучшение: снижение нагрузки в 5 раз

**3. Response Time 95th percentile**
Текущее состояние: 3-6 секунд для сложных запросов
С кешированием: 0.2, 0.5 секунд
Улучшение: в 12-15 раз

**4. Concurrent Users Capacity**
Текущее состояние: 20, 30 операторов одновременно
С кешированием: 100+ операторов одновременно
Улучшение: в 3, 4 раза

### Влияние на бизнес-метрики

**1. Operator Productivity**
Текущее состояние: 8, 10 заказов в час на оператора
С кешированием: 15, 20 заказов в час на оператора
Ожидаемое улучшение: +80% производительности

**2. Order Processing Time**
Текущее состояние: 30% времени тратится на ожидание загрузки
С кешированием: 95% времени на полезную работу
Ожидаемое улучшение: сокращение времени обработки на 25%

**3. Customer Satisfaction (B2B)**
Текущее состояние: жалобы на медленную обработку заказов
С кешированием: быстрая обработка, улучшение SLA
Ожидаемое улучшение: +40% удовлетворенности B2B клиентов

**4. System Scalability**
Текущее состояние: система близка к пределу по количеству операторов
С кешированием: возможность роста команды операторов в 3 раза
Ожидаемый эффект: поддержка роста бизнеса без дополнительной инфраструктуры БД

## Выбор элементов системы для кеширования

### Приоритет 1: MES списки заказов

**Что кешировать:**
1. **Основной список заказов** по статусам (PRICE_CALCULATED, MANUFACTURING_APPROVED, MANUFACTURING_STARTED, etc.)
2. **Фильтрованные списки** по типу клиента (B2B/B2C), дате создания, приоритету
3. **Агрегированные данные** количество заказов по статусам, статистика по операторам
4. **Детали заказа** информация о конкретном заказе (используется при открытии карточки)

**Обоснование приоритета:**
Это самая частая операция в MES (операторы обновляют список каждые 1-2 минуты), именно здесь основные жалобы на производительность.

### Приоритет 2: Справочные данные

**Что кешировать:**
1. **Список операторов** и их статусы (онлайн/офлайн)
2. **Конфигурация статусов** заказов и переходы между ними
3. **Настройки фильтров** пользовательские предпочтения операторов
4. **Метаданные файлов** информация о 3D файлах без самих файлов

### Приоритет 3: Расчетные данные

**Что кешировать:**
1. **Результаты расчета стоимости** для похожих 3D моделей
2. **Промежуточные результаты** расчетов сложности моделей
3. **Статистика производительности** операторов и времени выполнения

## Предлагаемое решение

### Выбор типа кеширования: Серверное кеширование

**Почему серверное, а не клиентское:**

**Серверное кеширование (выбираем):**
Централизованное управление данными, все операторы видят актуальную информацию одновременно, возможность инвалидации кеша при изменении данных, снижение нагрузки на базу данных

**Клиентское кеширование (не подходит):**
Разные операторы могут видеть разные данные, сложность синхронизации при изменениях, увеличение размера фронтенд приложения, проблемы с консистентностью данных

### Выбор паттерна кеширования: Cache-Aside

**Почему Cache-Aside:**

**Cache-Aside (выбираем):**
Приложение полностью контролирует логику кеширования, простота реализации и отладки, возможность кеширования только нужных данных, легкость обработки cache miss ситуаций

**Write-Through (не подходит):**
Каждая запись в БД требует записи в кеш, увеличивается время записи, избыточное кеширование редко используемых данных, сложность реализации для сложных запросов

**Refresh-Ahead (не подходит):**
Сложность предсказания какие данные нужно обновлять, избыточная нагрузка на систему при обновлении неиспользуемых данных, сложность реализации и мониторинга

### Техническая архитектура

**Кеш-сервер: Redis Cluster**
Высокая производительность (100K+ ops/sec), поддержка сложных структур данных (списки, хеши), встроенная репликация и кластеризация, TTL для автоматической инвалидации

**Интеграция с MES API:**
```csharp
public class OrderCacheService
{
    private readonly IRedisClient _redis;
    private readonly IOrderRepository _orderRepository;
    
    public async Task<List<Order>> GetOrdersByStatus(string status)
    {
        string cacheKey = $"orders:status:{status}";
        
        // Пытаемся получить из кеша
        var cachedOrders = await _redis.GetAsync<List<Order>>(cacheKey);
        if (cachedOrders != null)
        {
            return cachedOrders;
        }
        
        // Cache miss идем в БД
        var orders = await _orderRepository.GetByStatusAsync(status);
        
        // Сохраняем в кеш на 5 минут
        await _redis.SetAsync(cacheKey, orders, TimeSpan.FromMinutes(5));
        
        return orders;
    }
}
```

**Кеширование на уровне API:**
```csharp
[HttpGet("orders")]
[CacheResponse(Duration = 300)] // 5 минут
public async Task<IActionResult> GetOrders(
    [FromQuery] string status,
    [FromQuery] int page = 1,
    [FromQuery] int pageSize = 20)
{
    var orders = await _orderCacheService.GetOrdersByStatus(status);
    var pagedResult = orders.Skip((page - 1) * pageSize).Take(pageSize);
    
    return Ok(pagedResult);
}
```

Диаграммы последовательности для операций чтения списка заказов и изменения статуса заказа представлены в отдельном файле `caching_sequence_diagrams.drawio`.

## Стратегия инвалидации кеша

### Сравнение стратегий инвалидации

| Первая стратегия | Вторая стратегия | Остальные стратегии |
|------------------|------------------|---------------------|
| **Временная (TTL)** | **По ключу (Key-based)** | **Программная (Event-driven)** |
| Лучше подходит, потому что: Простота реализации, автоматическая защита от "забытых" кешей, не требует сложной логики отслеживания зависимостей | Позволяет сделать: Точную инвалидацию при изменениях, поддержание консистентности данных, мгновенное обновление связанных кешей | **Полная очистка:** Не позволяет сделать гранулярную инвалидацию, потеря всех кешированных данных |
| Есть особенности: 1) Возможны устаревшие данные до истечения TTL 2) Не подходит для критически важных real-time обновлений | Не позволяет сделать: Автоматическую защиту от забытых кешей, простую реализацию без отслеживания зависимостей | **Event-driven:** Высокая сложность реализации, зависимость от надежности доставки событий |

### Рекомендуемая стратегия: Комбинированная

**1. Временная инвалидация (TTL) - базовая защита**
```csharp
// Основные списки 5 минут
await _redis.SetAsync("orders:status:APPROVED", orders, TimeSpan.FromMinutes(5));

// Справочники 1 час  
await _redis.SetAsync("operators:list", operators, TimeSpan.FromHours(1));

// Детали заказа 2 минуты
await _redis.SetAsync($"order:details:{orderId}", orderDetails, TimeSpan.FromMinutes(2));
```

**2. Инвалидация по ключу - для критических изменений**
```csharp
public async Task InvalidateOrderCaches(string orderId, string oldStatus, string newStatus)
{
    var keysToInvalidate = new[]
    {
        $"orders:status:{oldStatus}",
        $"orders:status:{newStatus}",
        $"order:details:{orderId}",
        "orders:summary",
        "orders:statistics"
    };
    
    await _redis.DeleteAsync(keysToInvalidate);
}
```

**3. Event-driven инвалидация для real time обновлений**
```csharp
public class OrderStatusChangedHandler : INotificationHandler<OrderStatusChanged>
{
    public async Task Handle(OrderStatusChanged notification, CancellationToken cancellationToken)
    {
        // Инвалидируем кеши
        await _cacheService.InvalidateOrderCaches(
            notification.OrderId, 
            notification.OldStatus, 
            notification.NewStatus
        );
        
        // Уведомляем клиентов через SignalR
        await _hubContext.Clients.All.SendAsync("OrderStatusChanged", notification);
    }
}
```

### Обоснование выбора комбинированной стратегии

**Почему не только временная:**
Операторы могут видеть устаревшую информацию до 5 минут, что критично для быстро меняющихся статусов заказов

**Почему не только по ключу:**
Сложно отследить все зависимости между данными, возможны ошибки в логике инвалидации

**Почему не только event-driven:**
Высокая сложность реализации, возможны проблемы с доставкой событий

**Комбинированный подход решает все проблемы:**
TTL защищает от забытых кешей, key-based обеспечивает точность, event-driven дает мгновенность обновлений

## Альтернативные решения

### Решение 1: Клиентское кеширование + localStorage

**Описание:**
Кеширование данных в браузере оператора с использованием localStorage/sessionStorage и периодическая синхронизация с сервером.

**Плюсы:**
Минимальная нагрузка на сервер, мгновенный отклик UI, работа в offline режиме, простота начальной реализации

**Минусы:**
Проблемы с консистентностью данных между операторами, сложность синхронизации при изменениях, ограничения размера localStorage (5,10MB), проблемы с безопасностью данных

### Решение 2: Database level кеширование (Query Cache)

**Описание:**
Использование встроенных механизмов кеширования PostgreSQL или добавление read-replica для чтения данных.

**Плюсы:**
Прозрачность для приложения, автоматическая инвалидация при изменении данных, меньше изменений в коде, надежность

**Минусы:**
Ограниченная гибкость кеширования, нагрузка все равно идет на БД, сложность масштабирования, зависимость от конкретной СУБД

### Сравнительная таблица решений

| Критерий | Серверное (Redis) | Клиентское | Database Cache |
|----------|-------------------|------------|----------------|
| **Производительность** | Отличная | Отличная | Хорошая |
| **Консистентность** | Отличная | Плохая | Отличная |
| **Масштабируемость** | Отличная | Ограниченная | Средняя |
| **Сложность реализации** | Средняя | Низкая | Низкая |
| **Гибкость** | Отличная | Средняя | Ограниченная |
| **Безопасность** | Отличная | Средняя | Отличная |
| **Стоимость инфраструктуры** | Средняя | Низкая | Низкая |

### Заключение по выбору

**Выбираем серверное кеширование с Redis** как основное решение по следующим причинам:

1. **Критичность консистентности:** Операторы должны видеть актуальную информацию о заказах
2. **Требования к производительности:** Необходимо кардинальное улучшение времени отклика
3. **Масштабируемость:** Планируется рост количества операторов
4. **Гибкость:** Возможность точной настройки стратегий кеширования

**Дополнительно можем использовать клиентское кеширование** для:
Статичных справочных данных (список статусов, настройки UI), пользовательских предпочтений (фильтры, сортировка), временного хранения форм при потере связи

### Заключение

**Рекомендуется Решение 1 (Серверное кеширование с Redis)** по следующим причинам:

1. **Критичность консистентности данных:** В MES системе операторы должны видеть актуальную информацию о заказах одновременно, чтобы избежать конфликтов при назначении заказов.

2. **Масштабируемость бизнеса:** Планируется рост команды операторов в 3 раза, что требует централизованного решения.

3. **Интеграция с существующей архитектурой:** Redis легко интегрируется с текущим C# стеком и RabbitMQ для event-driven инвалидации.

4. **Долгосрочная перспектива:** Серверное кеширование обеспечивает основу для дальнейшего развития системы (analytics, ML, reporting).

**Возможность комбинирования:** Решение 1 можно дополнить элементами Решения 2 для статичных данных (настройки UI, пользовательские предпочтения), что даст максимальную производительность при сохранении консистентности критических данных.

Внедрение кеширования кардинально улучшит производительность MES системы и позволит операторам эффективно работать с растущим объемом заказов, что напрямую скажется на удовлетворенности B2B клиентов скоростью обработки их заказов.
