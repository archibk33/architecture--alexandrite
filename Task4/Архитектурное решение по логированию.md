# Архитектурное решение по логированию

## Анализ системы и проблемных мест

### Текущие проблемы требующие логирования

**1. Потерянные заказы**
- Клиенты жалуются, что их заказы пропадают
- Нет способа отследить путь заказа через все системы
- Сложно понять, на каком этапе заказ "застрял"

**2. Проблемы производительности MES**
- Операторы жалуются на медленную загрузку страниц
- Нет данных о том, какие операции тормозят систему
- Отсутствует информация о нагрузке на компоненты

**3. Проблемы с B2B API**
- Партнеры жалуются на потерянные заказы через API
- Нет логов взаимодействия с внешними клиентами
- Сложно диагностировать проблемы интеграции

**4. Отсутствие видимости бизнес-процессов**
- Нет данных о времени обработки заказов
- Отсутствует информация о паттернах использования
- Сложно выявить узкие места в процессах

## Необходимые логи с уровнем INFO

### Бизнес-события заказов

**Shop API:**
- Создание заказа: `timestamp`, `order_id`, `customer_id`, `customer_type` (B2C/B2B), `order_amount`
- Загрузка 3D файла: `timestamp`, `order_id`, `file_name`, `file_size_mb`, `upload_duration_ms`
- Изменение статуса заказа: `timestamp`, `order_id`, `old_status`, `new_status`, `user_id`
- Отправка заказа в очередь: `timestamp`, `order_id`, `queue_name`, `message_id`

**MES API:**
- Получение заказа на расчет: `timestamp`, `order_id`, `calculation_complexity`, `file_path`
- Начало расчета стоимости: `timestamp`, `order_id`, `calculation_worker_id`
- Завершение расчета: `timestamp`, `order_id`, `calculated_price`, `calculation_duration_minutes`
- Назначение заказа оператору: `timestamp`, `order_id`, `operator_id`
- Смена статуса производства: `timestamp`, `order_id`, `old_status`, `new_status`, `operator_id`

**CRM API:**
- Получение заказа для подтверждения: `timestamp`, `order_id`, `seller_id`
- Подтверждение производства: `timestamp`, `order_id`, `seller_id`, `confirmed_price`
- Отклонение заказа: `timestamp`, `order_id`, `seller_id`, `rejection_reason`

**RabbitMQ события:**
- Отправка сообщения: `timestamp`, `queue_name`, `message_id`, `correlation_id`, `message_type`
- Получение сообщения: `timestamp`, `queue_name`, `message_id`, `correlation_id`, `consumer_id`
- Ошибка доставки: `timestamp`, `queue_name`, `message_id`, `error_reason`

### Технические события

**HTTP запросы (все API):**
- Входящий запрос: `timestamp`, `method`, `endpoint`, `user_id`, `session_id`, `request_size_kb`
- Ответ на запрос: `timestamp`, `method`, `endpoint`, `response_code`, `response_time_ms`, `response_size_kb`

**База данных (Shop DB, MES DB):**
- Выполнение запроса: `timestamp`, `query_type`, `table_name`, `execution_time_ms`, `rows_affected`
- Ошибка базы данных: `timestamp`, `query`, `error_code`, `error_message`

**S3 Storage:**
- Загрузка файла: `timestamp`, `file_path`, `file_size_mb`, `upload_duration_ms`
- Скачивание файла: `timestamp`, `file_path`, `download_duration_ms`, `requester_service`

## Использование других уровней логирования

### DEBUG уровень
**Когда использовать:**
- Детальная отладка алгоритмов расчета стоимости в MES
- Пошаговое выполнение бизнес-логики
- Отладка интеграций с внешними системами

**Примеры:**
- Промежуточные результаты расчета стоимости
- Детали парсинга 3D файлов
- Шаги валидации данных заказа

### WARN уровень
**Когда использовать:**
- Потенциально проблемные ситуации, которые не критичны
- Превышение пороговых значений
- Неоптимальное поведение системы

**Примеры:**
- Расчет стоимости занимает больше 15 минут
- Размер 3D файла превышает 50MB
- Количество активных сессий превышает обычное
- Очередь RabbitMQ содержит больше 100 сообщений

### ERROR уровень
**Когда использовать:**
- Ошибки, которые мешают обработке заказов
- Проблемы интеграции между системами
- Недоступность внешних сервисов

**Примеры:**
- Ошибка сохранения заказа в базу данных
- Недоступность S3 хранилища
- Ошибка отправки сообщения в RabbitMQ
- Падение расчета стоимости в MES

### FATAL уровень
**Когда использовать:**
- Критические ошибки, требующие немедленного вмешательства
- Полная недоступность сервиса

**Примеры:**
- Недоступность базы данных
- Критическая ошибка MES API
- Переполнение диска

## Мотивация

### Почему системе нужно логирование

**Текущие болевые точки:**
1. **Поиск проблем занимает часы** - когда клиент жалуется на потерянный заказ, команда тратит 4-8 часов на поиск причины
2. **Отсутствие visibility в production** - невозможно понять, что происходит с заказами в реальном времени
3. **Потеря доверия B2B клиентов** - партнеры уходят из-за невозможности отследить свои заказы
4. **Реактивный подход** - проблемы обнаруживаются только после жалоб клиентов

**Что даст логирование:**
1. **Прозрачность бизнес-процессов** - полная видимость пути заказа от создания до завершения
2. **Быстрая диагностика** - сокращение времени поиска проблем с часов до минут
3. **Проактивное выявление проблем** - обнаружение проблем до жалоб клиентов
4. **Основа для оптимизации** - данные для улучшения производительности и процессов

### Влияние на технические метрики

**1. Mean Time To Detection (MTTD)**
- *Текущее состояние:* проблемы обнаруживаются через часы/дни после возникновения
- *С логированием:* автоматическое обнаружение аномалий за минуты
- *Улучшение:* в 50-100 раз

**2. Mean Time To Resolution (MTTR)**
- *Текущее состояние:* 4,8 часов на диагностику проблемы
- *С логированием:* 15,30 минут на понимание root cause
- *Улучшение:* в 10,15 раз

**3. System Observability**
- *Текущее состояние:* 15% видимости в системе
- *С логированием:* 90% покрытие критических процессов
- *Улучшение:* в 6 раз

**4. Error Detection Rate**
- *Текущее состояние:* обнаруживается 30% проблем (через жалобы)
- *С логированием:* автоматическое обнаружение 95% проблем
- *Улучшение:* в 3 раза

### Влияние на бизнес-метрики

**1. Customer Satisfaction (CSAT)**
- *Текущее состояние:* низкая оценка из-за потерянных заказов
- *С логированием:* быстрое решение проблем, прозрачность статуса
- *Ожидаемое улучшение:* +30% CSAT

**2. Order Loss Rate**
- *Текущее состояние:* приблизительно 5% заказов теряются или зависают
- *С логированием:* проактивное выявление и решение проблем
- *Ожидаемое улучшение:* снижение до 0.5%

**3. B2B Partner Retention**
- *Текущее состояние:* потеря крупных контрактов из-за проблем с API
- *С логированием:* полная трассируемость B2B заказов
- *Ожидаемый эффект:* сохранение всех текущих партнеров

**4. Support Team Productivity**
- *Текущее состояние:* 70% времени тратится на поиск проблем
- *С логированием:* 70% времени на решение проблем клиентов
- *Ожидаемое улучшение:* +50% производительности

**5. Revenue Protection**
- *Текущее состояние:* потери из-за багов в production и недовольства клиентов
- *С логированием:* предотвращение потери клиентов и заказов
- *Ожидаемый эффект:* защита 15-20% выручки

## Приоритизация систем для внедрения

### Первая очередь (критически важно)

**1. Shop API** 
*Приоритет: ВЫСШИЙ*
- Точка входа всех B2C заказов
- Интеграция с B2B партнерами
- Максимальное влияние на customer experience

**2. MES API**
*Приоритет: ВЫСШИЙ*  
- Узкое место системы (расчет стоимости)
- Критичная точка для B2B интеграций
- Основной источник жалоб на производительность

**3. RabbitMQ**
*Приоритет: ВЫСОКИЙ*
- Связующее звено между всеми системами
- Место потери сообщений
- Критично для отслеживания потока заказов

### Вторая очередь (важно)

**4. CRM API**
*Приоритет: СРЕДНИЙ*
- Влияет на время подтверждения заказов
- Важно для отслеживания работы продавцов
- Менее критично для основного потока

**5. Базы данных (Shop DB, MES DB)**
*Приоритет: СРЕДНИЙ*
- Важно для диагностики проблем производительности
- Помогает оптимизировать запросы
- Дополняет логи приложений

### Третья очередь (желательно)

**6. S3 Storage**
*Приоритет: НИЗКИЙ*
- Проблемы возникают редко
- Легко диагностируются другими способами
- Не критично для основных бизнес-процессов

**7. Frontend приложения (Vue, React)**
*Приоритет: НИЗКИЙ*
- Проблемы видны пользователям напрямую
- Меньше влияют на бизнес-процессы
- Можно отложить на потом

## Предлагаемое решение

### Выбор технологического стека

**Центральная система логирования: ELK Stack**
- **Elasticsearch** - хранение и индексирование логов
- **Logstash** - агрегация и парсинг логов
- **Kibana** - визуализация и поиск
- **Filebeat** - сбор логов с серверов

**Обоснование выбора ELK:**
- Масштабируемость для растущих объемов логов
- Мощные возможности поиска и анализа
- Богатая экосистема и интеграции
- Open source с возможностью расширения
- Совместимость с существующей инфраструктурой

### Архитектура системы логирования

**Уровень сбора:**
- **Filebeat agents** на каждом сервере приложений
- Сбор логов из файлов и отправка в Logstash
- Буферизация при недоступности центральной системы

**Уровень обработки:**
- **Logstash cluster** для обработки потока логов
- Парсинг структурированных логов (JSON format)
- Обогащение метаданными (environment, service_name)
- Фильтрация и нормализация данных

**Уровень хранения:**
- **Elasticsearch cluster** с репликацией
- Автоматическое создание индексов по датам
- Настроенные mapping'ы для оптимального поиска
- ILM (Index Lifecycle Management) для управления жизненным циклом

**Уровень визуализации:**
- **Kibana dashboards** для разных ролей пользователей
- Готовые dashboard'ы для мониторинга заказов
- Настроенные поисковые запросы для типовых задач

### Стандартизация логов

**Единый формат логов (JSON):**
```json
{
  "timestamp": "2024-01-20T10:30:00.123Z",
  "level": "INFO",
  "service": "shop-api",
  "environment": "production",
  "correlation_id": "order-12345-uuid",
  "event_type": "order_status_changed",
  "order_id": "12345",
  "customer_id": "customer-67890",
  "details": {
    "old_status": "SUBMITTED",
    "new_status": "PRICE_CALCULATED",
    "user_id": "user-123"
  },
  "performance": {
    "duration_ms": 150,
    "memory_mb": 45
  }
}
```

**Обязательные поля:**
- `timestamp` - точное время события
- `level` - уровень логирования  
- `service` - имя сервиса
- `correlation_id` - сквозной идентификатор заказа
- `event_type` - тип события для группировки

**Контекстные поля:**
- `order_id`, `customer_id`, `user_id` - бизнес-идентификаторы
- `session_id` - идентификатор пользовательской сессии
- `request_id` - идентификатор HTTP запроса

### Интеграция с приложениями

**Shop API (Java Spring Boot):**
```java
// Структурированное логирование
@Component
public class OrderLogger {
    private static final Logger logger = LoggerFactory.getLogger(OrderLogger.class);
    
    public void logOrderStatusChange(String orderId, String oldStatus, String newStatus) {
        MDC.put("correlation_id", "order-" + orderId);
        MDC.put("event_type", "order_status_changed");
        MDC.put("order_id", orderId);
        
        logger.info("Order status changed from {} to {}", oldStatus, newStatus);
        
        MDC.clear();
    }
}
```

## Политика безопасности для логов

### Защита чувствительных данных

**Автоматическая маскировка:**
- **Персональные данные**: имена, адреса, телефоны → хеширование или замена на `[MASKED]`
- **Финансовые данные**: номера карт, CVV коды → полное удаление
- **Пароли и токены**: любые auth данные → полное удаление
- **API ключи**: замена на частичное отображение `key_abc***xyz`

**Конфигурация фильтров в Logstash:**
```ruby
filter {
  # Маскировка номеров карт
  mutate {
    gsub => ["message", "\d{4}-\d{4}-\d{4}-\d{4}", "[CARD_MASKED]"]
  }
  
  # Удаление паролей из query параметров
  mutate {
    gsub => ["message", "password=[^&\s]+", "password=[REDACTED]"]
  }
}
```

## Политика хранения логов

### Стратегия индексирования

**Разделение по типам данных:**

**Бизнес-логи** (`logs-business-*`):
- Логи заказов, изменений статусов, бизнес-событий
- Наиболее важные для анализа проблем
- Длительное хранение и быстрый доступ

**Технические логи** (`logs-technical-*`):  
- HTTP запросы, ошибки приложений, производительность
- Важны для диагностики технических проблем
- Среднее время хранения

**Системные логи** (`logs-system-*`):
- Логи операционной системы, инфраструктуры
- Важны для мониторинга здоровья системы
- Короткое время хранения

**Audit логи** (`logs-audit-*`):
- Логи доступа к данным, изменений конфигурации
- Требования compliance
- Длительное хранение в архиве

### Lifecycle Management

**Hot tier (быстрые SSD)** - 0-30 дней:
- Все новые логи попадают сюда
- Максимальная скорость поиска и анализа
- Полная доступность для всех операций

**Warm tier (медленные диски)** - 30-90 дней:
- Автоматический перенос старых данных
- Доступны для поиска, но медленнее
- Сжатие для экономии места

**Cold tier (архивное хранилище)** - 90 дней - 2 года:
- Долгосрочное хранение для compliance
- Очень медленный доступ
- Максимальное сжатие

**Delete** - старше 2 лет:
- Автоматическое удаление
- Исключения для критических audit логов

### Оценка объемов хранения

**Расчет на основе нагрузки:**

**Shop API** (1000 заказов/день):
- 1000 заказов × 5 логов/заказ × 1KB = 5MB/день
- Месяц: 150MB, Год: 1.8GB

**MES API** (1000 расчетов/день):
- 1000 расчетов × 10 логов/расчет × 1KB = 10MB/день  
- Месяц: 300MB, Год: 3.6GB

**HTTP логи** (10,000 запросов/день):
- 10,000 запросов × 2 лога/запрос × 0.5KB = 10MB/день
- Месяц: 300MB, Год: 3.6GB

**Итого в год:** ~15GB логов

**С учетом роста (100% в год):** 30GB в первый год

**Индексы и репликация:** ×3 = 90GB

**Рекомендуемая емкость кластера:** 200GB с запасом на 2 года

### Детальный анализ критериев

#### 1. Критерий: Лицензионная модель и vendor lock-in

**ELK Stack:**
**Минусы:** Elastic License v2 ограничивает коммерческое использование некоторых фич, **Vendor lock-in:** Привязка к Elastic N.V., **Риски:** Возможные изменения лицензии в будущем

**OpenSearch:**
**Плюсы:** Полностью открытая Apache License 2.0, **Независимость:** Управляется Linux Foundation, **Форк Elasticsearch:** Совместимость с существующими решениями

**Splunk:**
**Минусы:** Полностью проприетарная, очень дорогая, **Vendor lock-in:** Полная зависимость от Splunk Inc., **Лицензирование:** По объему данных (очень дорого при росте)

**Вывод:** OpenSearch и Loki побеждают по открытости

#### 2. Критерий: Совокупная стоимость владения (TCO)

**Расчет для нашей нагрузки (~30GB логов в год):**

**ELK Stack:**
Инфраструктура: $200/месяц (3 ноды Elasticsearch), Лицензии: $0 (базовая версия), Поддержка: $500/месяц (опционально), **Итого:** $200-700/месяц

**OpenSearch:**
Инфраструктура: $200/месяц (аналогично ELK), Лицензии: $0, Поддержка: $0-300/месяц (community/AWS), **Итого:** $200-500/месяц

**Splunk:**
Лицензии: $150/GB/год × 30GB = $4500/год = $375/месяц, Инфраструктура: $100/месяц, Поддержка: включена, **Итого:** $475/месяц (минимум)

**Loki + Grafana:**
Инфраструктура: $100/месяц (меньше ресурсов), Лицензии: $0, **Итого:** $100/месяц

**Вывод:** Loki самое дешевое, OpenSearch лучший баланс цена/функциональность

#### 3. Критерий: Производительность и масштабируемость

**Тесты производительности (events/second):**

| Решение | Индексация | Поиск | Хранение |
|---------|------------|-------|----------|
| **ELK** | 50,000 | Очень быстрый | Высокое потребление |
| **OpenSearch** | 50,000 | Очень быстрый | Высокое потребление |
| **Splunk** | 100,000+ | Быстрый | Эффективное сжатие |
| **Loki** | 20,000 | Средний | Очень эффективное |
| **ClickHouse** | 1,000,000+ | Сверхбыстрый | Отличное сжатие |

**Для нашей нагрузки (1000 заказов/день = ~100 events/sec):**
Все решения справятся с текущей нагрузкой, нужен запас на рост в 10-100 раз, ELK/OpenSearch оптимальны для наших объемов

#### 4. Критерий: Экосистема и интеграции

**ELK Stack:**
Огромная экосистема плагинов, готовые интеграции с Java, C#, Python, множество готовых dashboard'ов, большое комьюнити

**OpenSearch:**
Совместимость с экосистемой Elasticsearch, все плагины ELK работают, AWS интеграции, меньше готовых решений

**Splunk:**
Enterprise интеграции (SIEM, ITSM), готовые apps для различных систем, дорогие дополнительные модули

**Loki:**
Native интеграция с Grafana/Prometheus, меньше готовых интеграций, растущая, но небольшая экосистема

#### 5. Критерий: Простота эксплуатации

**Сложность настройки (1-5, где 5 = очень сложно):**

| Решение | Первоначальная настройка | Ongoing поддержка | Troubleshooting |
|---------|--------------------------|-------------------|-----------------|
| **ELK** | 4 | 3 | 3 |
| **OpenSearch** | 4 | 3 | 3 |
| **Splunk** | 2 | 2 | 2 |
| **Loki** | 2 | 2 | 3 |
| **ClickHouse** | 5 | 4 | 4 |

**Требования к экспертизе команды:**
**ELK/OpenSearch:** Нужен DevOps с опытом Elasticsearch, **Splunk:** Можно обучить быстро (GUI-интерфейс), **Loki:** Простая настройка, но меньше документации, **ClickHouse:** Требует глубокую экспертизу

#### 6. Критерий: Функциональность поиска и анализа

**Возможности поиска:**

**ELK/OpenSearch:**
Мощный Query DSL, Full-text search, агрегации и аналитика, Machine Learning (X-Pack)

**Splunk:**
SPL (Search Processing Language), статистический анализ, Machine Learning Toolkit, Correlation Search

**Loki:**
LogQL (ограниченный по сравнению с SQL), нет full-text search, ограниченная аналитика, хорошо для временных рядов

### Обоснование выбора: OpenSearch

**Почему OpenSearch, а не ELK:**

1. **Лицензионные риски:** Elastic может изменить лицензию в будущем
2. **Открытость:** Apache License 2.0 гарантирует свободу использования
3. **Совместимость:** 100% совместимость с ELK экосистемой
4. **AWS поддержка:** Managed сервис доступен в облаке
5. **Комьюнити:** Растущее Open Source комьюнити

**Почему не Splunk:**
Слишком дорого для стартапа ($4500+ в год только лицензии), vendor lock-in с проприетарным форматом данных, overkill для наших текущих потребностей

**Почему не Loki:**
Ограниченные возможности поиска (нет full-text search), меньше готовых интеграций, не подходит для complex log analysis

**Почему не ClickHouse:**
Слишком сложен в настройке и поддержке, требует специфическую экспертизу, overkill для наших объемов данных

### Общий вывод

**Выбираем OpenSearch** как основное решение:

**Immediate benefits:**
Совместимость с ELK tutorials и решениями, свобода от лицензионных ограничений, возможность миграции с ELK без изменений

**Long-term benefits:**
Независимость от vendor decisions, возможность кастомизации под наши нужды, managed options в AWS/Azure

**Migration path:**
1. Начать с OpenSearch вместо Elasticsearch
2. Использовать стандартные Logstash и Kibana/OpenSearch Dashboards
3. При росте переход на managed AWS OpenSearch Service

**Fallback strategy:**
Если OpenSearch не подойдет, легкая миграция обратно на ELK, все конфигурации и dashboard'ы будут совместимы, минимальные изменения в application code
Внедрение логирования позволит трансформировать операционную модель компании от реактивной к проактивной, обеспечив полную видимость бизнес-процессов и технической инфраструктуры.
Система логирования станет foundation для всех дальнейших улучшений observability и автоматизации операций.
