# Планирование: анализ, идентификация проблем и поиск решений

## Какие проблемы я вижу в системе

### Проблемы с архитектурой

Мне кажется, самая большая проблема это то, что у нас всё в единственном экземпляре. По сути, если что то упадёт, всё встанет. 

Вот что я заметил:

**С масштабированием беда:**
- У каждого приложения только один сервер
- Базы данных тоже одиночки, без всяких дублей
- Load balancer'ов нет вообще, хотя они могли бы помочь распределить нагрузку
- Кеша нет никакого, поэтому каждый раз лезем в базу за одними и теми же данными

**С надёжностью тоже проблемы:**
- Если что-то сломается, автоматически не восстановится
- Нет никаких резервных копий сервисов
- Нет retry-механизмов, поэтому если запрос не прошёл, так и останется

**Сообщения теряются:**
- В RabbitMQ сообщения могут потеряться, и мы об этом не узнаем
- Нет dead letter queue, тема для «мёртвых» сообщений (читал тут - https://www.rabbitmq.com/docs/dlx)
- Не следим за тем, как работают очереди
- API работает синхронно, может зависнуть надолго

### Операционные заморочки

**Мониторинга нет:**
- Мы не видим, что происходит с системой в реальном времени
- Не можем проследить путь заказа от начала до конца
- Логи раскиданы по разным местам
- Когда что-то ломается, мы узнаём от клиентов, а не от системы

**MES тормозит:**
- Первая страница загружается очень медленно
- С большими данными система справляется плохо
- Запросы к базе неоптимальные
- Плохо работаю фильтры и пагинация

**С процессами разработки тоже не очень:**
- Релизы задерживаются из-за ручного тестирования
- Автотестов толком нет
- Деплоим всё руками
- Производительность не проверяем автоматически

### Бизнес страдает

**Клиенты недовольны:**
- Заказы не приходят вовремя
- Крупные партнёры уходят из-за проблем с API
- Никто не знает, где сейчас его заказ
- Расчёт стоимости может занять полчаса (очень больно)

**Операторы мучаются:**
- Не видят новые заказы сразу
- Не понятно, какие заказы важнее
- Нагрузка распределяется неравномерно
- Сложно понять, на каком этапе заказ

## Мои идеи, как это всё починить

В целом, написал список предложений, которые могут оказать позитивный эффект на архитектуру 

### Инфраструктурные штуки

**Идея 1: Сделать приложения масштабируемыми**
- Поставить по несколько серверов для каждого приложения
- Добавить load balancer'ы, чтобы нагрузка распределялась
- Настроить автоматическое масштабирование 

Я думаю, это поможет выдержать рост нагрузки, который у нас каждый месяц +100 заказов.

**Идея 2: Сделать базы данных надёжнее**
- Настроить репликацию PostgreSQL (основной и резервный)
- Если основная база упадёт, резервная автоматически подхватит
- Добавить автоматические бэкапы

**Идея 3: Починить очереди сообщений**
- Настроить dead letter queue в RabbitMQ
- Сделать так, чтобы сообщения гарантированно доходили
- Добавить повторные попытки отправки

Мне кажется, это самое важное, потому как сейчас заказы теряются именно из-за проблем с сообщениями.

### Ускорение системы

**Идея 4: Добавить кеширование**
- Поставить Redis для часто используемых данных
- Кешировать прямо в приложениях
- Может быть, даже CDN для картинок и файлов

**Идея 5: Оптимизировать работу с базой**
- Найти медленные запросы и переписать их
- Добавить индексы там, где их не хватает
- Сделать нормальную пагинацию

Операторы жалуются на медленную загрузку, по идеи это им поможет

**Идея 6: Сделать обработку асинхронной**
- Расчёт стоимости перевести в фоновый режим
- API будет сразу отвечать "принято в обработку"
- Добавить webhook'и для уведомлений о готовности

### Видимость системы

**Идея 7: Мониторинг**
- Поставить Prometheus + Grafana для метрик
- Следить за всеми сервисами и железом
- Настроить алерты, чтобы сразу знать о проблемах

**Идея 8: Трейсинг заказов**
- Внедрить Jaeger или Zipkin (альтернатива егерю)
- Добавить correlation ID для каждого заказа
- Видеть весь путь заказа через систему

Это поможет понять, где именно заказы теряются

**Идея 9: Централизованные логи**
- Поставить ELK stack (Elasticsearch, Logstash, Kibana)
- Собрать все логи в одном месте
- Сделать единый формат логирования

### Процессы разработки

**Идея 10: Автоматизировать тестирование**
- Написать больше unit тестов
- Добавить E2E тесты
- Проверять производительность автоматически

**Идея 11: Улучшить CI/CD**
- Автоматизировать деплой везде
- Добавить blue green deployment
- Сделать автоматические откаты при проблемах

### Для пользователей

**Идея 12: Сделать MES удобнее**
- Обновления списка заказов в реальном времени
- Умная приоритизация заказов
- Dashboard с важными метриками

**Идея 13: Прозрачность для клиентов**
- Отслеживание статуса заказа онлайн
- Уведомления об изменениях
- Показывать примерное время выполнения

1. Насколько это критично для бизнеса

Мне кажется, без этого дальше работать бессмысленно. Мы не видим проблем, пока клиенты не пожалуются.

- **Идея 4: Кеширование** - быстро поможет с производительностью MES

- **Идея 6: Асинхронная обработка** - API перестанет зависать

### Средний приоритет (4-6 месяцев):

- **Идея 11: CI/CD улучшения** - тоже не самое критичное пока
- **Идея 13: Прозрачность для клиентов** - важно, но не горит

## Как я вижу систему через полгода

Если мы сделаем хотя бы основные вещи из списка, система должна стать намного лучше. Вот как я это представляю:

### Инфраструктура
- У каждого приложения будет 2,3 сервера за load balancer
- Базы данных будут с репликацией, не боимся что всё упадёт
- Redis для кеширования, чтобы не долбить запросами базу постоянно

### Видимость
- Мониторинг всего, со-но видим проблемы до того, как клиенты звонят
- Трейсинг каждого заказа, понимаем что где застярло
- Все логи в одном месте, можно нормально искать

### Надёжность
- Сообщения в RabbitMQ не теряются
- Если что-то не работает, система пробует ещё раз
- API работает асинхронно, не зависает

### Процессы
- Автотесты помогают быстрее выпускать релизы
- Мониторинг предупреждает о проблемах заранее
- Клиенты довольны, потому что заказы не теряются

## Три главные задачи на полгода

Если честно, у нас ресурсов не очень много, поэтому я выбрал самое важное. Вот три вещи, которые надо сделать в первую очередь

### 1. Мониторинг и трейсинг

**Почему это важно:**
Сейчас мы работаем вслепую. Когда что-то ломается, мы узнаём от клиентов, а потом часами ищем проблему. 

**Что получим:**
- Будем находить проблемы за полчаса вместо 8 часов
- Узнаем о проблемах раньше клиентов
- Поймём, как система реально работает

Я думаю, без этого дальше развиваться невозможно.

### 2. Ускорение MES и кеширование

**Почему это важно:**
Операторы каждый день жалуются на медленную работу. Они не могут нормально работать, а от них зависит весь производственный процесс.

**Что получим:**
- Страницы будут загружаться в 3, 5 раз быстрее
- База данных перестанет задыхаться от запросов
- Операторы смогут обработать больше заказов

Это прямо влияет на производительность всей компании.

### 3. Надёжность сообщений

**Почему это важно:**
Заказы теряются из-за проблем с RabbitMQ. Клиенты платят деньги, а заказ пропадает.

**Что получим:**
- Заказы перестанут теряться
- API будет работать быстрее (асинхронно)
- B2B клиенты перестанут уходить
